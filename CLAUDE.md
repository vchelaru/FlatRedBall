# Orchestration preferences

- Do NOT use `isolation: "worktree"` (Agent tool) or a manual `git worktree add` for this repo. Glue's `.csproj` files pull Gum source in via relative paths to the sibling `Gum` repo (e.g. `..\..\..\..\..\Gum\GumDataTypes\...`); a worktree nested under `.claude/worktrees/<name>/` adds directory levels those relative paths don't account for, so Glue can't be built or opened in Visual Studio from one — this blocks manual testing entirely. Do repo work directly in the primary checkout instead (one branch at a time), fast-forwarded to fresh `origin/NetStandard` before starting.
- **Two human gates per issue.** (1) Research is read-only: investigate until implementation is mechanical, post the plan as a comment on the tracking issue, then stop and wait for the user's go-ahead before writing any code. (2) Open the PR but never merge it — leave it for review. Waivable only by an explicit up-front instruction: "do it all" (or similar) skips gate 1; merging requires being told to merge, and "do it all" alone does not grant it. Only one agent may hold gate 1's go-ahead at a time — the user serializes writes, so never self-authorize implementation because another issue's plan looks idle.
- Do not create new GitHub issues for follow-up/deferred work. Add a comment to the existing tracking issue instead.
- PR descriptions must NOT use closing keywords ("Closes #N", "Fixes #N") against the tracking issue — merging a PR should not auto-close it. Reference the issue plainly (e.g. "Part of #N") instead. Only close the tracking issue manually once its full scope is done.
- Work ends when the PR is opened. Report and stop; don't start the next issue on your own.
- Every subagent's final report must include what it got stuck on / what took the most time or retries, even if it ultimately succeeded — this feeds back into improving skills and process, not just task completion.
