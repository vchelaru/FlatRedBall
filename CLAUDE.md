# Orchestration preferences

- **Any code change (not skills/docs) happens in a worktree, whether or not there's a tracked issue.** Default to doing repo work directly in the primary checkout only for read-only investigation/debugging; the moment it turns into an edit, set up a sibling worktree (see placement rule below) first. Skill/agent/CLAUDE.md file edits are exempt and can be made directly in the primary checkout.
- Do NOT use `isolation: "worktree"` (Agent tool) — it hardcodes worktrees under `.claude/worktrees/<name>/`, which breaks Glue's relative-path `ProjectReference`s into the sibling `Gum` repo (e.g. `..\..\..\..\..\Gum\GumDataTypes\...`) and blocks building or opening in Visual Studio. Manual worktrees are fine as long as they're placed as a sibling of `FlatRedBall` (same level as `Gum`) under `GitHub\`, e.g. `git worktree add ../FlatRedBall-<name> -b <branch> origin/NetStandard`, then `EnterWorktree` with `path` to switch into it — the sibling placement preserves the same relative-path depth to `Gum`, so it builds normally. Call `EnterWorktree` right away, before any edits — running commands via absolute paths from the primary checkout works but leaves the status-bar cwd wrong, which is the whole point of switching. Exception: `EnterWorktree` on a sibling path asks the user for permission (creating the worktree and editing files in it do not), and a subagent cannot enter a sibling path at all. Subagents, and any run while the user is away, use absolute paths instead. Otherwise do repo work directly in the primary checkout (one branch at a time), fast-forwarded to fresh `origin/NetStandard` before starting.
- **A worktree only isolates FRB -> Gum, not Gum -> FRB.** Gum's `GumCore.DesktopGlNet6.csproj` back-references `..\..\..\..\FlatRedBall\` by that exact folder name (its engine `ProjectReference`s and the `GumCoreShared.FlatRedBall.projitems` import), so anything built through a Gum project (source-linked samples, the `FormsSampleProject` gold tests) compiles the *primary* checkout's engine and `GumPlugin\Embedded`, not the worktree's. Before trusting such a build from a worktree, fast-forward the primary checkout to `origin/NetStandard`; a worktree change to those files cannot be verified that way at all.
- **One human gate per issue: open the PR but never merge it** — leave it for review; merging requires being told to merge explicitly. Research folds directly into implementation with no separate plan-comment/approval stop — do the implementation work in its own worktree (see placement rule above) so multiple issues can proceed concurrently without conflicting.
- **When the user has authorized merging a run of PRs, don't wait for CI on each one.** CI takes about 20 minutes and every merge forces the next PR to rebase and rerun it. Merge once the PR is rebased on fresh `origin/NetStandard` and its targeted tests plus the fast suite pass locally. At a stopping point, run full CI on the branch with `gh workflow run pr-tests.yml --ref NetStandard` and fix what it finds.
- Do not create new GitHub issues for follow-up/deferred work — remaining scope of the issue you are working, split out of the current PR. Add a comment to its tracking issue instead. This does **not** cover an unrelated bug you merely tripped over along the way: that gets its own issue, because a comment on an issue about something else disappears the moment that issue closes. Test: would this still need doing if the issue you are on were cancelled? If yes, file it. The one exception is a CI failure (a platform project that no longer builds, a flaky test): it is fixed on the PR where it shows up, even when the cause predates the PR, and gets no issue of its own.
- Use closing keywords ("Closes #N", "Fixes #N") when the PR actually resolves the whole issue. When it only covers part of a multi-PR issue, reference it plainly ("Part of #N") so merging doesn't close work that isn't done, and close the issue manually once the rest lands.
- Work ends when the PR is opened. Report and stop; don't start the next issue on your own.
- Every subagent's final report must include what it got stuck on / what took the most time or retries, even if it ultimately succeeded — this feeds back into improving skills and process, not just task completion.
- **New sample and repro projects default to code-only, not a Glue project.** `Samples/MonoGameExtendedParticles` is the shape: one `.csproj` with a `ProjectReference` to `FlatRedBallDesktopGLNet6`, plus a copy of `Content/Shader.xnb`, which `FlatRedBallServices.InitializeFlatRedBall` loads at startup and crashes without. Reach for a Glue project only when the sample is about Glue itself. A code-only sample builds in CI with a plain `dotnet build` and has no generated code to regenerate first.
- **Do implementation work in-session, not via subagents/forks.** Long-running or tool-heavy work (build cycles, TDD loops) stays in this session so its output — including worktree/cwd changes — is directly visible, even though that means it blocks the conversation and fills this session's context. Don't spawn an `Agent`/fork for FlatRedBall implementation work without being asked.
- **All skills and agents live in the repo-root `.claude/`.** Don't create a nested `.claude/skills` under a subfolder (e.g. `FRBDK/Glue`): skills there never show up in a session started at the repo root.
- **`/frb-skills/` holds 3rd-party skills for game developers using FlatRedBall (GlueCli, etc.).** These are the public, distributable skill set; `/.claude/skills/` is for engine and editor contributors only. The 3rd-party skills are also surfaced under `/.claude/skills/<name>` via local symlinks (gitignored). Edit the canonical copy under `/frb-skills/`. Run `scripts/link-skills.ps1` after cloning and after adding, renaming, or removing an `frb-skills/` folder; it creates the links and regenerates their `.gitignore` block.
- **Before saying a test harness doesn't exist or planning a new one, load the `test-harnesses` skill and `ls` every `TestSupport` folder.** Grepping for the names of the classes under test misses harnesses, because harnesses are named for what they do (launch, load, build), not for what they test.
- **Verification lives in automated tests, never in manual checks.** Every behavior a change touches, including editor paths a refactor reroutes, gets a test that exercises it the way the editor or CLI does. Running the exe or the editor by hand is a smoke check, not evidence, and is never handed to the user as a step.
- **Edit C# files with the Edit/Write tools, not sed/python heredocs through Bash.** Repo files are CRLF with a UTF-8 BOM; heredoc edits silently miss on CRLF, strip the BOM (noisy one-line diffs), and lose `\` in string literals. When grepping build output for errors, never `head`-limit it: a hidden compile error leaves a stale test DLL that reports "passed".
