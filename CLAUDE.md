# Orchestration preferences

- Do NOT use `isolation: "worktree"` (Agent tool) — it hardcodes worktrees under `.claude/worktrees/<name>/`, which breaks Glue's relative-path `ProjectReference`s into the sibling `Gum` repo (e.g. `..\..\..\..\..\Gum\GumDataTypes\...`) and blocks building or opening in Visual Studio. Manual worktrees are fine as long as they're placed as a sibling of `FlatRedBall` (same level as `Gum`) under `GitHub\`, e.g. `git worktree add ../FlatRedBall-<name> -b <branch> origin/NetStandard`, then `EnterWorktree` with `path` to switch into it — the sibling placement preserves the same relative-path depth to `Gum`, so it builds normally. Otherwise do repo work directly in the primary checkout (one branch at a time), fast-forwarded to fresh `origin/NetStandard` before starting.
- **One human gate per issue: open the PR but never merge it** — leave it for review; merging requires being told to merge explicitly. Research folds directly into implementation with no separate plan-comment/approval stop — do the implementation work in its own worktree (see placement rule above) so multiple issues can proceed concurrently without conflicting.
- Do not create new GitHub issues for follow-up/deferred work — remaining scope of the issue you are working, split out of the current PR. Add a comment to its tracking issue instead. This does **not** cover an unrelated bug you merely tripped over along the way: that gets its own issue, because a comment on an issue about something else disappears the moment that issue closes. Test: would this still need doing if the issue you are on were cancelled? If yes, file it.
- Use closing keywords ("Closes #N", "Fixes #N") when the PR actually resolves the whole issue. When it only covers part of a multi-PR issue, reference it plainly ("Part of #N") so merging doesn't close work that isn't done, and close the issue manually once the rest lands.
- Work ends when the PR is opened. Report and stop; don't start the next issue on your own.
- Every subagent's final report must include what it got stuck on / what took the most time or retries, even if it ultimately succeeded — this feeds back into improving skills and process, not just task completion.
